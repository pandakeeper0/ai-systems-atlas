# Hash Functions · 哈希函数

> 哈希函数最重要的不是“把数据变短”，而是把任意长度输入映射到固定长度摘要，并让攻击者难以逆向、伪造或主动构造有用的碰撞。

## 1. 最基本的模型

哈希函数可以写成：

[
H:{0,1}^{*}ightarrow{0,1}^{n}
]

其中输入可以是任意长度，输出固定为 (n) bit。对于文件哈希，算法通常按块处理输入并不断更新固定大小的内部状态，因此可以流式计算，不需要把整个文件一次加载进内存。

若输入长度为 (N)，普通顺序实现的工作量通常与输入字节数成正比，因此可近似理解为：

[
O(N)
]

## 2. 为什么碰撞一定存在？

输入空间无限，而 (n) bit 输出只有 (2^n) 种可能。根据鸽巢原理，一定存在：

[
x
eq y,qquad H(x)=H(y)
]

密码学并不要求“绝对没有碰撞”，而要求：

[
oxed{	ext{攻击者在现实计算资源下找不到有用的碰撞}}
]

对于理想的 (n)-bit 哈希，寻找任意碰撞的通用生日攻击大约需要 (2^{n/2}) 次工作；寻找某个给定摘要的原像大约需要 (2^n) 次工作。

## 3. 三个核心安全性质

### Preimage Resistance · 抗原像

已知 (h=H(x))，难以找到任意 (x') 使 (H(x')=h)。

### Second-preimage Resistance · 抗第二原像

已知一份具体输入 (x)，难以找到另一个 (x'
eq x) 使：

[
H(x')=H(x)
]

### Collision Resistance · 抗碰撞

攻击者可以同时自由选择两份输入，但仍难以找到：

[
x
eq y,qquad H(x)=H(y)
]

数字签名尤其依赖哈希在相应攻击模型下保持足够的碰撞安全性。

## 4. CRC32 和密码学哈希不是一类东西

CRC 本质上是有限域上的多项式余数计算，适合检测随机位翻转、传输错误和常见 burst error，但没有设计成抵抗主动攻击者。

[
oxed{	ext{CRC：校验随机错误，不提供密码学完整性}}
]

攻击者若能修改数据，通常也能相应调整 CRC。

MD5、SHA-1、SHA-2、SHA-3 等密码学哈希则以抗原像、抗第二原像、抗碰撞等性质为安全目标。

## 5. MD5 / SHA-1 为什么淘汰？

关键不是“哈希短，所以可以直接反解”。

真正的问题是研究者找到了远快于通用生日攻击的结构化碰撞攻击。这些攻击利用内部差分传播规律，让两条不同消息路径最终收敛到相同摘要。

因此：

[
oxed{	ext{碰撞攻击成功}
eq	ext{原像攻击成功}}
]

MD5 和 SHA-1 被淘汰，主要是因为碰撞安全性已被实用性攻击破坏，而不是因为能够直接从摘要恢复原文。

工程上应将 MD5 / SHA-1 视为历史兼容算法，不再用于新的安全设计。

## 6. SHA-256：串行 chaining construction

SHA-256 属于 SHA-2 家族。消息 padding 后被分块，每一块通过 compression function 更新 chaining state：

[
S_{i+1}=F(S_i,M_i)
]

因此：

[
S_0ightarrow S_1ightarrow S_2ightarrowcdotsightarrow S_k
]

单条消息的标准 SHA-256 计算天然按块串行推进。

安全性并不是简单来自“串行”，而来自整体构造与压缩函数设计，包括位运算、模加、轮常数和充分混合。

目前没有已知可实际利用、足以破坏 SHA-256 核心安全性的攻击。

## 7. Length-extension Attack · 长度扩展攻击

Merkle–Damgård 类构造具有重要的长度扩展性质。若错误地把普通哈希直接拿来做消息认证，例如：

[
operatorname{MAC}=H(secretparallel message)
]

攻击者在某些条件下可以利用已知摘要继续计算扩展消息的摘要，而不需要知道 secret。

正确做法是使用专门设计的：

[
oxed{operatorname{HMAC}}
]

例如 HMAC-SHA-256。

长度扩展并不意味着 SHA-256 “被破解”，而是说明普通哈希不能被随意拼装成认证协议。

## 8. SHA-3：Sponge Construction · 海绵结构

SHA-3 基于 Keccak，采用 sponge construction：

[
	ext{absorb}ightarrow	ext{permute}ightarrow	ext{squeeze}
]

内部状态通常分为 rate 与 capacity。它与 SHA-2 的 chaining construction 明显不同，也不具有 SHA-256 那类长度扩展性质。

但不要把 SHA-3 理解成“SHA-256 注定会被它替代”。两者都是现代、标准化且目前安全的密码学哈希家族。工程选择还取决于生态、硬件支持、协议标准和兼容性。

标准 SHA3-256 对一条消息也不是“任意并行”的。若需要大规模树形并行哈希，应使用专门设计的 tree-hash / parallel-hash 方案。

## 9. 哈希校验、HMAC、数字签名分别解决什么？

### 普通哈希校验

发布：

[
file,qquad H(file)
]

可以检测随机损坏。但攻击者如果能同时替换文件和公开摘要，普通哈希无法验证“是谁发布的”。

### HMAC

双方共享秘密密钥：

[
tag=operatorname{HMAC}_k(message)
]

它可提供消息完整性和来源认证，但不能让不持有共享密钥的第三方独立验证。

### Digital Signature · 数字签名

典型流程：

[
messageightarrow H(message)ightarrow	ext{private-key signature}
]

验证者使用公钥验签。

如果底层哈希出现足够强、足够可控的碰撞攻击，可能影响依赖该哈希的签名体系；真实风险取决于协议、签名格式以及攻击者能否制造 chosen-prefix collision 等满足协议约束的输入。

## 10. 密码存储：不要直接存 SHA-256(password)

“抗原像”不等于“普通 SHA-256 适合密码存储”。

人类密码熵通常很低，而 SHA-256 又非常快。数据库泄露后，攻击者可以高速尝试字典和暴力候选。

密码应使用专门的 password hashing / KDF，例如：

[
oxed{	ext{Argon2id / scrypt / bcrypt / PBKDF2}}
]

并为每个密码使用随机 salt。

这里的目标恰恰是让每次猜测都更昂贵，从而提高离线破解成本。

## 11. 如果未来 SHA-256 出现实用攻击

这会是严重的密码学迁移事件，但不等于“互联网瞬间全部失效”。

影响取决于：

- 被攻破的是碰撞、第二原像还是原像；
- 攻击成本；
- 是否支持 chosen-prefix 等更强控制；
- 上层协议怎样使用哈希；
- 系统是否具备算法 agility。

典型迁移会是：

[
	ext{旧算法}ightarrow	ext{新旧兼容 / 双算法}ightarrow	ext{新算法}
]

如果原始数据仍然存在，很多对象都可以重新计算新的摘要。只有只剩旧摘要、原文已经不存在的场景，才无法从旧摘要直接得到新哈希。

## 12. 串行不等于安全，并行也不等于不安全

安全来自整个设计：

[
oxed{	ext{构造方式 + 压缩/置换函数 + 域分离 + 合并规则 + 密码分析}}
]

树哈希可以将消息分块并行处理，再通过安全的合并结构归约：

[
H_1,H_2,ldots,H_n
ightarrow
	ext{tree reduction}
ightarrow
H_{root}
]

只要设计正确，并行并不会天然削弱密码学安全。

## 13. 一页速查

| 算法 / 机制 | 核心定位 | 密码学安全 | 关键注意点 |
| --- | --- | --- | --- |
| CRC32 | 随机错误检测 | 否 | 不防主动攻击 |
| MD5 | 旧密码学哈希 | 否 | 碰撞已实用攻破 |
| SHA-1 | 旧密码学哈希 | 否 | 碰撞已实用攻破 |
| SHA-256 | SHA-2 密码学哈希 | 是 | 直接构造存在长度扩展性质 |
| SHA3-256 | Sponge 密码学哈希 | 是 | 构造不同，无 SHA-2 式长度扩展 |
| HMAC-SHA-256 | 消息认证 | 是 | 用于共享密钥完整性 / 认证 |
| Argon2id 等 | 密码存储 | 是 | 故意慢且耗资源，并配合 salt |

## 14. Mental model

[
oxed{	ext{Hash 不负责证明“是谁”，只把内容映射成稳定摘要}}
]

[
oxed{	ext{CRC 防随机错误；密码学 Hash 还要抵抗主动构造}}
]

[
oxed{	ext{碰撞一定存在，但安全哈希让找到有用碰撞变得不可行}}
]

[
oxed{	ext{签名、HMAC、密码存储是不同问题，不能只靠“更强哈希”混在一起}}
]

工程上只记住：

1. 文件完整性：使用 SHA-256 / SHA-3 等现代哈希。
2. 消息认证：使用 HMAC 或标准 AEAD / MAC，不要手搓 Hash(secret || message)。
3. 密码存储：使用 Argon2id 等 password KDF，不要直接 SHA-256。
4. 数字签名：使用现代标准签名方案和协议规定的哈希算法。
5. MD5 / SHA-1：只做历史兼容，不再用于安全设计。
